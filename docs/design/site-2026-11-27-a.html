Secure communication systems.

A private messenger with no company in the middle.

You add a server that you, or someone you know, runs. Messages are sealed on your phone, wait on that server only until they have been collected, and are then wiped. The server can never read them.

How it works

Four steps, and none of them involves us.

  1. Someone runs a server

    You, a friend, your club. One small program on any Linux machine with a public address. It needs no domain name and no certificate authority.

    $ docker compose up -d --build

  2. You add it by scanning a QR code

    The code carries the server's fingerprint. From then on your phone talks only to the machine that holds that key, even if someone else takes over its address.

    Server fingerprint
    znpepjc55xy7et44kfchuw5zdhaqtoe5r6hfxzkyddzbxkup2erq

  3. You talk in channels

    A channel is a group chat with one owner. Only the owner lets people in or removes them, and the owner's phone signs the member list. The server cannot add anyone.

    Family · member list, version 7
    • Sam owner · signed this list
    • Gran member
    • Alex member

  4. Messages are collected, then wiped

    Once every member's phone has a message, the server overwrites its copy. If a phone stays away, the copy goes when it reaches the channel's maximum message age.

    collected by everyone  → wiped
maximum age reached    → wiped

Left out on purpose

What it does not have

  • accountNo phone number, no email address, no password. Your phone's keys are your identity.
  • central serviceThis website is information only. The app never contacts it.
  • delivery reports or read receiptsNobody is told when, or whether, you collected a message.
  • push serviceThe app keeps its own connection to your servers. Nothing about your messages passes through Google.
  • history on the serverA server holds a message until it is collected, and no longer.
  • adverts, analytics or trackingIn the app, on the server, or on this website.

Built in

What it does have

  • End-to-end encryption that moves onEvery message uses the next key and the used key is destroyed. Keys taken from a phone later cannot open messages recorded earlier.
  • A fresh identity on every serverTwo servers cannot tell that the same phone uses both.
  • Safety numbersThirty digits that two people compare, or scan, to be sure nobody is in the middle.
  • Invites as a QR code or a linkFor a server or for a channel. The app opens the link itself; no website is involved.
  • Four ways onto a serverAn invite, a password, approval of each new device, or open to anyone. The person running it chooses.
  • Quiet notificationsThey say only "New message" unless you choose to show more.

Before you choose it

What this design costs you.

Keeping nothing on a server and tying your identity to your phone has consequences. They are deliberate, and you should know them first.

  • Lose your phone, lose your messagesAnd your place in every channel. There is no backup and no way to sign in again.
  • New members see nothing from beforeNeither does a new phone. The server has no history to give.
  • A channel depends on its owner's phoneIf the owner loses it, the channel can no longer change. Members can still leave.
  • Someone has to run the serverAnd keep its key file safe.
  • It uses some batteryStaying connected without a push service is not free.
  • Text only, Android only, for nowPictures, audio and video are planned.

Build it yourself

The source for the app and the server is at github.com/edward-b-1/decentralizeddeaddrop, with build instructions.

Run a server

One program, one folder, one port.

A Dead Drop server makes its own key, and phones recognise it by that key's fingerprint. It needs no domain name, no certificate authority and no other service. The smallest VPS a provider sells is enough, because it holds messages only until they are delivered.

  1. Get a Linux machine with a public address

    Ubuntu 24.04 or later is what the guide assumes. Note its IP address, or point a hostname at it. Whichever you choose goes into every invite, with port 7443.

  2. Lock it down

    The set-up script creates your user, turns off password logins, opens only SSH and port 7443, switches on automatic security updates and installs Docker.

    # bash setup-vps.sh <your-username> "<your SSH public key>"

  3. Get the code and say where the server is

    $ git clone https://github.com/edward-b-1/decentralizeddeaddrop.git
$ cd decentralizeddeaddrop/deploy
$ cp env.example .env
$ nano .env        # set DEADDROP_PUBLIC to <your address>:7443

  4. Start it

    The first build takes a few minutes. The log of the first start shows the fingerprint, a one-time operator token, and a link and QR code holding both.

    docker compose logs deaddropdfirst start
    $ docker compose up -d --build
$ docker compose logs --no-log-prefix deaddropd
    Made this server's key (/data/deaddrop.key.pem) and certificate (/data/deaddrop.cert.pem).
Keep the key file safe and backed up: phones recognise the server by it.

  5. Become the operator

    In the app: Servers, Add a server, Scan a QR code, and point the phone at the terminal. That phone now runs the server: it switches the ways in on and off, makes invites and approves devices.

    From the operator's phone: Servers, your server, Invite a device. Each invite lets one new phone on, once.

Prefer no Docker? The server is a single program with a systemd unit file. The full guide covers that, updating, and using a certificate of your own.

What the server logs

One line for each request, with no address and no identifier in it. The single exception is a wrong server password, which is logged with the address it came from so that a firewall tool can block the guesser.

2026-11-26T18:20:05Z password-failure from=203.0.113.7

Someone who knows the password is never recorded, and neither is anyone using another way in.

How it works

What protects your messages, and what does not.

A plain account of the design. The full specification, including the decisions still open, is PROTOCOL.md in the source.

Not independently reviewed. The encryption library this is built on, vodozemac from the Matrix project, was audited in 2022. Decentralized Dead Drop itself has had no outside review. Treat it accordingly.

Knowing it is the right server

Every connection uses TLS 1.3. The server has a private key, and its fingerprint is a hash of the matching public key, written as 52 letters and digits. The fingerprint travels in every invite link and QR code.

A phone that has the fingerprint accepts exactly the server that holds that key. It does not ask a certificate authority, so it works the same for a bare IP address as for a hostname. Someone who takes over the server's address does not have its key, and the app refuses them.

If you type an address by hand there is no fingerprint to check against, so the app shows you the one it found and asks you to compare it with the person who runs the server. After that the phone remembers it, and refuses any server that does not hold the same key.

Who you are

There is no phone number, email address or password. Your phone makes its identity keys in its secure hardware, and those keys are your account.

You get a fresh identity for every server, so two servers cannot tell that the same phone uses both. The name people see is a label you choose in each channel.

Safety numbers

Any two members can compare thirty digits, or scan them as a QR code. Matching numbers mean each phone holds the other's real keys. This is what catches a server that tries to slip a device of its own into a channel under someone else's name.

Channels and the member list

A channel is a group chat on one server. A two-person conversation is a channel with two members.

Whoever creates a channel owns it. Joining takes an invite from the owner, after which you ask to join and the owner lets you in. Nobody is put in a channel without asking.

The owner's phone signs the whole member list, and every change is a new list with a higher version. Phones never accept an older one. So the server cannot add a member, and cannot keep one the owner removed.

How messages are sealed

This is the design Signal uses for groups and the one Matrix uses. Each phone has its own sending ratchet for each channel: every message uses the next key, and the used key is destroyed. Phones hand their ratchets to one another through private sessions between each pair of devices.

A phone winds its receiving ratchets forward past each message it has opened. Neither that message nor anything earlier can be opened again from what the server held, even by someone who later takes the phone.

Sending ratchets are replaced whenever the member list changes, so a removed member gets nothing new and a new member gets nothing old. Messages are padded to fixed sizes (256 bytes, then doubling), so every short text looks the same size.

What it does not protect against

No messenger protects against everything. These are the limits of this one.

  • Someone with your unlocked phoneThey can read what is on it. Messages already opened are stored on the phone, encrypted with a key in its secure hardware.
  • Being seen to use itA server, and anyone watching the network, can see that your phone connects, when, and roughly how much. They cannot see what is said.
  • BlockingAnyone in the middle, or the server, can stop messages getting through. Nothing prevents that.
  • A member who copies what they readEncryption ends at the people in the channel.
  • Mistakes in this softwareIt is new and unreviewed. The source is public so that it can be checked.

Privacy policy

We receive nothing.

The app has no account with us, no connection to any server of ours, no analytics, no adverts and no crash reporting. It talks only to the servers you add to it, which are run by you or by people you know.

Decentralized Dead Drop is made by an individual developer. Last updated 27 November 2026.

What the app keeps on your phone

  • Your identity keys, in the phone's secure hardware. They never leave it.
  • For each server you add: its address and fingerprint, your channels, their members' names, your message history, and the everyday keys that seal and open messages. These are stored encrypted with a key held in the phone's secure hardware, and are left out of phone backups.
  • Two settings: whether to stay connected in the background, and whether notifications show message text.

Removing a server in the app destroys your keys and history for it. Uninstalling the app destroys all of it.

The camera and notifications

The camera is used only to scan QR codes, when you ask it to. Pictures are read on the phone and are neither kept nor sent anywhere. Notifications are made on the phone itself: the app uses no push service.

This website

It sets no cookies, runs no analytics and loads nothing from anyone else. Its server keeps no log of visitors or downloads.

What goes to a server you add

A server is run by whoever gave you its address, and they are responsible for it. By design it receives as little as possible.

  • It can see a device ID that the app makes for that server alone (not a hardware identifier); the names of the channels you are in; the name you chose in each; who else is in them; when messages pass through and their size to the nearest step; and the network address you connect from.
  • It cannot see what your messages say.
  • It keeps messages only until every member has received them, or until the maximum age the channel's owner has set, and then wipes them.
  • Its log records no addresses and no identifiers, with one exception: an address that gets the server's password wrong.

Taking a server off your phone deletes your device, your place in its channels and the channels you own from that server.
